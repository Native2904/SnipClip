Linking screenshots with StickySnips

A screenshot and a matching note should be recognizable as belonging together, without having to type out a name. Dragging a file directly onto another single file isn't supported by TC or Windows - drop targets are always folders. So the link is formed simply by both files living in the same subfolder:

StickySnips\tcmd\Lister\
    note.snip
    screenshot.bmp

The folder name carries the actual meaning here - StickySnips otherwise have no freely chosen name, just an automatic preview built from the first characters of the content.

Standalone image pins

A screenshot can also be dragged straight from ! Screenshots into a normal, single-level category (StickySnips\Pictures\) with no note involved at all - same as text. Keeping several images together this way is just an ordinary category with several entries. The depth of the path decides which case applies: one level = standalone pin, two levels = a link.

Delete behavior

No matter which side of a link gets deleted, only the link itself dissolves - the other element stays fully intact. A deleted image moves back to ! Screenshots; a deleted note only breaks the link, the image stays. Same logic as history↔StickySnip: delete one, the other (independently existing) one is untouched. This doesn't apply to standalone image pins (one level) - those are genuinely deleted, since there's no counterpart there to preserve.

Visibility in the screenshots folder

Inside a sticky subfolder, both files sit visibly side by side. Under ! Screenshots itself, though, only images live there, with no visible connection to a note. The Verknuepft column shows the linked note's name there (blank = unlinked) - same custom-column mechanism already used for the existing ones (Edited/Diff/Source/Age).

Storage limit

Two independent limits, since image size varies far more than text ever does:

[image_capture]
max_screenshots=50
max_total_size_mb=200

Whichever hits first trims the oldest screenshot.

Icons

Linked entries get their own chain-link icon instead of the source-app icon - "this is linked" is more useful at a glance than "this came from which program". Unlinked entries show the real icon of the source application instead (extracted from its .exe), or - if the source is unknown or that program no longer exists - a fallback icon, the built-in floating eye by default, freely replaceable with your own .ico via FallbackSourceIcon=.

Icon priority order: linked → real source-app icon → fallback icon → TC default.
